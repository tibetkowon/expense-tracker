# 월별 시트 관리 (Monthly Sheet Management) — 설계 문서

- 날짜: 2026-09-06
- 상태: 초안 (사용자 리뷰 대기)
- 배경: 사용자 실사용 피드백 5건 중 4번 항목("저장되는 sheet 파일명 관리")을 다룸. 나머지 4건(수정/삭제, 결제수단 select box 디자인, 저장위치 선택 화면 디자인, PWA 설치 프롬프트)은 별도로 처리한다.

## 1. 목적

현재 앱은 스프레드시트 파일 1개(`expense-tracker`, 고정명)에 헤더 없이 모든 지출을 한 시트(`Sheet1`)에 계속 append만 한다. 이 구조는 다음 문제가 있다:

- 파일 하나만 봐서는 헤더가 없어 가계부인지 알기 어렵고, AI가 파일을 열어 분석하기도 어려움
- 데이터가 쌓일수록 한 시트 안에 전체 이력이 뒤섞여, 특정 월만 보거나 관리하기 어려움
- 파일명이 고정되어 있어 사용자가 원하는 이름으로 바꿀 수 없음

이 스펙은 스프레드시트 파일은 1개로 유지하되, 그 안을 월별 시트(탭)로 나누고, 헤더 행을 추가하고, 파일명을 설정 가능하게 만드는 것을 다룬다.

## 2. 데이터 모델 / 시트 구조

- 스프레드시트 파일 수는 그대로 1개 (`findOrCreateSpreadsheet` 유지).
- 파일명은 기본값 `expense-tracker`를 유지하되, 설정 화면에서 사용자가 원하는 이름으로 변경 가능 (저장 위치 설정과 같은 위치/패턴, `localStorage` 기반, `folderStorage.ts`와 유사한 `fileNameStorage.ts` 형태로 분리).
- 파일명 변경은 "새 이름으로 파일을 새로 검색/생성"하는 것이 아니라, **기존 스프레드시트 파일 자체의 이름을 Drive API로 rename**하는 것이다. 새 이름으로 검색해서 찾지 못했다고 새 파일을 만들면 파일이 2개가 되어 "파일 수 1개 유지" 원칙이 깨지므로, 반드시 현재 파일을 식별한 뒤 이름만 바꾼다.
- 시트 탭은 월별로 `YYYY-MM` 형식(예: `2026-09`)으로 생성/조회한다. 정렬 순서가 자동으로 맞고 파싱하기 쉬워 사람이 보기엔 다소 기계적이어도 AI/수식 처리에 유리하다는 이유로 이 형식을 채택했다.
- 각 월 시트의 1행은 헤더: `날짜 | 금액 | 카테고리 | 메모 | 결제수단`.
- 기존 `renameFirstSheet`(2026-09-02, 스프레드시트 최초 생성 시 로케일에 따라 첫 탭 이름이 달라지는 버그를 우회하기 위한 로직)는 이번 변경으로 대체된다. 새 로직은 "첫 번째 시트가 Sheet1이어야 한다"는 가정 자체를 하지 않고, 필요한 월 시트를 이름으로 직접 찾거나 생성하므로 이 워크어라운드가 더 이상 필요 없다.

## 3. 마이그레이션 (기존 사용자 데이터)

기존 사용자는 이미 `Sheet1`에 헤더 없이 쌓인 데이터를 갖고 있다. 이를 자동으로, 1회성으로 이관한다.

- `findOrCreateSpreadsheet` 처리 과정에서 레거시 `Sheet1`(헤더 없는 기존 평면 구조)이 남아있는지 확인한다.
- 존재하면: 각 행을 `date` 필드 앞 7자리(`YYYY-MM`)로 그룹핑하여, 해당 월 시트(헤더 포함, 없으면 생성)로 옮겨 쓴다.
- 이관이 끝나면 `Sheet1` 탭은 삭제한다. 이관 후에도 원본을 남겨두면 사용자가 파일을 열었을 때 데이터가 이중으로 보이거나, 향후 합계 계산 시 혼란을 줄 수 있기 때문이다.
- 이미 이관된 파일에는 `Sheet1`이 없으므로, 이후 요청에서는 이 로직이 아무 동작도 하지 않는다 (멱등성 보장 — 재실행해도 안전).

## 4. API 변경

- `GET /api/expenses?folderId=...&month=2026-09` — `month` 쿼리 파라미터를 추가한다. 생략 시 이번 달 시트를 우선 조회하고, 이번 달 시트가 아직 없으면 존재하는 시트 중 가장 최근 월로 폴백한다.
- 응답에 `availableMonths: string[]`을 추가한다 (존재하는 월 시트 목록, 내림차순 정렬). 프론트엔드 월 선택 드롭다운에 그대로 사용된다.
- `POST /api/expenses` — 저장 대상 월을 요청 시각("오늘")이 아니라 입력된 `date` 필드 기준으로 결정한다. 지난 날짜로 소급 입력해도 해당 월 시트에 정확히 들어가며, 해당 월 시트가 없으면 자동 생성한다.
- `monthlyTotal` 계산은 이제 해당 월 시트에 속한 행만 합산하면 되므로 로직이 단순해진다. `summarizeByMonth`(`lib/summary.ts`)는 함수 자체는 유지하되, 이미 월 단위로 분리된 데이터에 적용한다.

## 5. UI / 월 선택 동작

- `ExpenseDashboard`가 로드 시 `/api/expenses`에서 `expenses` + `monthlyTotal` + `availableMonths`를 함께 받는다.
- `MonthlySummary` 인근에 월 선택 드롭다운을 추가한다. `availableMonths`만 옵션으로 노출하며, 기본값은 이번 달(없으면 가장 최근 월)이다.
- 드롭다운에서 다른 월을 선택하면 `?month=` 파라미터로 재조회하여 해당 월 데이터만 표시한다.
- 지출을 새로 저장하면, 저장된 `date`가 속한 월로 뷰가 자동 전환된다. 다른 월을 보고 있다가 오늘 지출을 입력해도 결과가 바로 보인다.
- 기존 `expenses.slice(-20)`(최근 20건 제한, `app/api/expenses/route.ts`)은 제거한다. 한 번에 한 달치 데이터만 다루므로 인위적인 개수 제한이 더 이상 필요 없다.

## 6. 이 스펙에서 다루지 않는 것

- 지출 행의 수정/삭제 기능(피드백 1번) — 이 스펙으로 시트 구조(헤더, 월별 분리)가 안정화된 뒤, 별도 스펙에서 행 식별 방식(시트 내 행 번호 기반 등)을 설계한다. 지금 구조 변경으로 향후 행 위치가 안정적인 기반이 마련된다.
- 결제수단 select box 디자인 버그, 저장위치 선택 화면 디자인, PWA 설치 프롬프트 — 별도로 처리.

## 7. 미해결 사항 / 향후 재검토

- 파일명 변경 UI의 정확한 위치와 문구는 구현 단계에서 결정 (기존 `FolderPickerSection`과 같은 영역에 배치 예정).
- 월 시트가 매우 많아졌을 때(수년 치) 드롭다운 UX는 현재 스코프 밖 — 필요 시 재검토.
